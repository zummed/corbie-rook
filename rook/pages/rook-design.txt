Rook design: the runs that answer a message, what each machine takes and gives, and who may do what.

Rook is ready-made Corbie machines. `corbie rook init` writes them into the
project's `.rook/`, which `.corbieignore` lists, so none of them has a
location. The project places each one it uses with a file of one line, and its
own machines, the routers, the conversation, the agents and their toolkits,
say what happens to a message.

What runs where
---------------

`corbie run submit .` records the project as one tree, `/my-bot` for a
directory named `my-bot`. Each `*.yaml` that `.corbieignore` does not list is a
machine at its path under `/my-bot`, without `.yaml`. For a bot named
`grouse` on Slack:

  /my-bot/grouse/slack/grouse             singleton: the router, and Rook's listener as its child run
  /my-bot/conversation                    keyed <service>:<chat>:<user>:assistant: one person in one thread
  /my-bot/agents/assistant                called by the conversation for each turn
  /my-bot/people/find                     called for who someone is: the lookup
  /my-bot/grouse/slack/chat/post          called to post a text
  /my-bot/grouse/slack/chat/ask           called: one question, waiting for a press
  /my-bot/grouse/slack/chat/show          called by the question: posts it on Slack, and closes it
  /my-bot/grouse/slack/assistant/status   called to show a status under a thread
  /my-bot/grouse/slack/files/get          called to download a message's files
  /my-bot/later                           transient: one run for each reminder the agent's tool later sets
  /my-bot/ballot                          keyed, one for each question an approval asks in several places: closes the others once one is answered
  /my-bot/answers                         keyed, one for each question: sends the question each press its router sends there

A run uses the secrets and values set at its location or above. `init` prints
the commands that set a service's at `/my-bot/grouse/<service>`, where the
router, its listener and the service's calls run. Rook's approval runs as a
child of the run that asks, at that run's location.

How a message is answered
-------------------------

1. The listener hears a message, and sends `message` to its parent, the router.
2. The router sends it to `conversation` with the key `<service>:<chat>:<user>:assistant`. A send to a key with no running run starts one.
3. The conversation's turn calls the lookup, shows a status, downloads the message's files, and calls `agents/assistant` with the person's scopes.
4. The conversation calls the bot's `chat/post` with the reply, where the message came from.

While it works, the agent may post a short message with its tool `progress`.
With its tool `later` it sets a reminder: after the minutes it chose, the run
at `later` sends the same conversation a message from the same person, marked
`later`, and the agent takes another turn.

Following a message
-------------------

Each send and each call names, in the sender's record, the run it went to, and
that run names the run and step that started it as its cause.

  corbie run ls --all              each run, its location, its key, and the run it is a child of
  corbie run show <id>             the run, with cause: the run and step whose send or call started it
  corbie run show <id> --record    each step of the run and its child runs, and each send or call with the run it went to

1. In the router's record, each message is a send to `/my-bot/conversation#<key>`, naming the conversation's run.
2. In the conversation's record, each turn is a child run, and the turn's call to `/my-bot/agents/assistant` names the agent's run.
3. The agent's record shows each tool as a job, a held tool as `hold <tool> for the ask`, and the approval as a child run, with a child run `place` for each place it asks, whose call to the bot's `chat/ask` names the question's run.
4. The question's record shows each press checked, and what the lookup gave for the presser.

These are the records of a message on Telegram whose agent opens the toolkit
`messages`, and calls `tell`, which waits for alice's yes. A record line is
shown without its time and run, and a name in angle brackets, such as
`<agent>`, stands for a run's ID.

    corbie run show <router> --record
      step 2  -> send message to /my-bot/conversation#telegram:1:1:assistant · started <conversation>
    corbie run show <conversation> --record
      step 3  -> job answering: a machine, <turn>
      step 1  -> job asker: a call to /my-bot/people/find, <find>
    corbie run show <agent> --record
      step 6  -> hold tell for the ask
      step 6  -> job ask: a machine, <approval>
      step 2  -> job question.0: a machine, <place>
      step 1  -> job asking: a call to /my-bot/grouse/telegram/chat/ask, <question>
      step 7  <- done from ask {"approved":["tell"],"note":"alice said yes."}
      step 7  -> job tell: a call to /my-bot/grouse/telegram/chat/post, <tell>
    corbie run show <question> --record
      step 4  -> job checking: a machine, <press>
      step 2  <- done from who {"email":"alice@example.com","name":"alice","scopes":["messages","messages:approve"]}

Who may talk to whom
--------------------

A file with no `receive:` takes sends and calls from every location of the
project. A written `receive:` takes them only from the locations it lists.
The client that submitted the project may send to and call every location,
and every other tree and client is refused.

  grouse/<service>/grouse.yaml     receive: []: no location; it takes events only from its listener, a child run
  .rook/<service>/listen.yaml      receive: []: no location; it sends its router only what its service gave
  conversation.yaml                receive: { message: [grouse/*/grouse, later], stop: [grouse/*/grouse] }: a router, and a reminder
  later.yaml                       receive: [agents/*]: only an agent's tool later
  ballot.yaml                      no receive:, so every location of the project
  answers.yaml                     no receive:, so every location of the project
  deploys.yaml                     receive: [grouse/slack/grouse]: only the router that sends to it
  .rook/agent.yaml                 receive: [conversation]; an agent a second conversation calls writes its own, naming both
  grouse/<service>/chat/ask.yaml   receive: [answers, agents/*, ballot]; an answer only from answers at its key, close only from its ballot
  grouse/<service>/chat/show.yaml  receive: [grouse/<service>/chat/ask]: only the question

A child run is addressed by its ID at its parent's location, and only its
own `receive:` applies to it, so a child of a trusted run writes its own, as
each listener does.

A sender needs `send:` for the location in its `allow:`.

  grouse/<service>/grouse.yaml     send:conversation, send:answers
  conversation.yaml                in its turn, send:people/find, send:agents/assistant, and the bot's files/get and status; in its reply, send:grouse/*/chat/post and send:grouse/slack/assistant/status
  .rook/approval.yaml              send:ballot, and in each place, send: for that place's question
  .rook/chat/ask.yaml              send: for its service's chat/show, for its ballot, and send:answers
  .rook/ballot.yaml                send:**, used only to answer a question that sent it opened
  .rook/answers.yaml               send:**, used only to send an answer on to the question that sent it open
  .rook/agent.yaml                 in its tool progress, send:*/*/chat/post; in its tool later, send:later
  .rook/later.yaml                 send: for the conversation the agent's input names
  .rook/shared/press.yaml          send: for the question's lookup
  a toolkit's tool                 a tool written call: holds send: for its location; a job writes its own allow:

- The lookup's answer is trusted because only the conversation calls the agent, only a router and `later` send to the conversation, and a router takes events only from its listener.
- A reminder acts for the person of the turn that set it: the tool `later` fixes the message's service, chat and user and the conversation's run from the agent's input, and the model chooses only the minutes and the note.
- A question trusts an answer from its router for the same reason: no location can send to the router or its listener, so each answer the router sends on came from the service. The run of `answers` at the question's key sends on only an answer from the question's router, and the question takes an answer only from that run.
- A ballot can only close a question as answered elsewhere, which the approval does not count, so a send to a ballot can make an approval no and never yes.
- A gateway is a client, so a gateway whose client submitted the project can call any of its locations with any input. Submit the project from a client no gateway uses.

The project's files
-------------------

`corbie rook init <dir> --bot <bot> --services <names>` writes these files,
and never one that is there. In a directory that is no project it writes them
all, but `conversation.yaml` only with `--bot`, and the files under
`<bot>/<service>/` only for the services `--services` names. In a project it
writes only `AGENTS.md`, `.corbieignore`, `answers.yaml`, `ballot.yaml`,
`later.yaml`, and with `--bot` the conversation and the files of the services
named, each when it is missing.

  .corbieignore                      .rook/ and people/scopes.yaml; init adds each when missing
  conversation.yaml                  keyed: one person, one thread and the agent
  people/find.yaml                   the lookup: include: .rook/people/file.yaml
  later.yaml                         a reminder; include: .rook/later.yaml
  ballot.yaml                        keyed: an approval asked in several places; include: .rook/ballot.yaml
  answers.yaml                       keyed: one question's presses; include: .rook/answers.yaml
  people/scopes.yaml                 each email's name and scopes, which the lookup reads
  <bot>/<service>/<bot>.yaml         singleton: the router, and Rook's listener as its child
  <bot>/<service>/chat/post.yaml     include: .rook/<service>/chat/post.yaml
  <bot>/<service>/chat/ask.yaml      include: .rook/chat/ask.yaml, with receive: and the service's router and chat/show
  <bot>/<service>/chat/show.yaml     include: .rook/<service>/chat/show.yaml, with receive:
  <bot>/slack/assistant/status.yaml  include: .rook/slack/assistant/status.yaml
  <bot>/telegram/chat/status.yaml    include: .rook/telegram/chat/status.yaml
  <bot>/<service>/files/get.yaml     include: .rook/<service>/files/get.yaml; on Jira attachment/get.yaml
  AGENTS.md, CLAUDE.md, .mcp.json    for a model that changes the project

`init` rewrites `.rook/` whole, with every service's machines, whichever
services the project has.

  .rook/<service>/listen.yaml        the listener, which a router runs as its child
  .rook/<service>/<service>.js       the service's script; each machine runs it with its own do:
  .rook/slack/                       chat/post, chat/show, assistant/status, files/get, files/upload, conversations/replies
  .rook/telegram/                    chat/post, chat/show, chat/status, files/get, files/send
  .rook/gitlab/                      chat/post, chat/show, issues/read, issues/notes/create, issues/notes/list, uploads/create, files/get, repository/files/read, repository/commits/create, pipeline/create, api.js
  .rook/jira/                        chat/post, chat/show, issue/comment/create, issue/comment/list, issue/attachments/create, attachment/get, api.js
  .rook/chat/ask.yaml                the question, the same on every service
  .rook/approval.yaml, approval.js   the ask a machine names
  .rook/people/file.yaml, file.js    the lookup that reads people/scopes.yaml
  .rook/agent.yaml                   included by an agent: its input, prompt, conversation, receive: and the tools progress and later
  .rook/later.yaml                   the reminder that later.yaml places
  .rook/ballot.yaml                  the ballot that ballot.yaml places
  .rook/answers.yaml                 the run for each question that answers.yaml places
  .rook/filters/                     words.yaml and words.js, a filter; model.yaml, included by an agent that is one
  .rook/shared/                      the scripts the conversation and the services share, and press.yaml
  .rook/AGENTS.md                    the page corbie rook manual rook, for a model

A router and its listener
-------------------------

A router is a singleton statechart of the project's. Its one state runs
Rook's listener as a child job, which sends `message`, `answer` and `stop` to
its parent, and names no other location. The router's rules say where each
goes.

    # grouse/slack/grouse.yaml
    statechart: grouse
    description: The router of grouse on Slack.
    lifetime: singleton
    receive: []
    allow: [send:conversation, send:answers]
    initial: listening
    states:
      listening:
        job: { machine: .rook/slack/listen.yaml, restart: { after: always } }
        on:
          message:
            when: "${!event.data.unaddressed && !event.data.change}"
            send: { to: { at: conversation, key: "${'slack:' + event.data.chat + ':' + event.data.user + ':assistant'}" }, event: message, data: "${event.data}" }
          stop:
            send: { to: { at: conversation, key: "${'slack:' + event.data.chat + ':' + event.data.user + ':assistant'}" }, event: stop, data: "${event.data}" }
          answer:
            send: { to: { at: answers, key: "${event.data.question}" }, event: answer, data: "${event.data}" }

- A rule can only send, and a send goes only to a statechart: a singleton's run, or a keyed run, which it starts. A post or a lookup is a call, so the conversation makes it.
- An answer goes only to a run of `answers`, whatever the button holds, which sends it on only to the question that opened it.
- `receive: []`, in the router and in Rook's listener, refuses a send from any location, so the router takes events only from its listener, and the listener sends only what its service gave.
- `restart: { after: always }` starts the listener again when it ends. A listener whose read fails waits, then reads again.
- A listener reads a value when it starts. After changing one, run `corbie run cancel /my-bot/grouse/<service>/grouse`, then `corbie run submit .`.

  Telegram    hears each message in a person's own chat with the bot, but /start; /stop, with any words after it, is a stop; a group's messages are logged
  Slack       hears a direct message and a message that names the bot over Socket Mode, an emoji added to a message, and a press of the stop button
  GitLab      asks every 30 seconds which issues changed, and reads their new comments and changes
  Jira        asks every 30 seconds what changed in each project

A listener sends a press of a question's button as `answer`, and so do the
GitLab and Jira listeners for a comment that answers a question. These
settings go in a listener's `input:`:

  overhear: true         Slack: hears a channel's message outside a thread, and a reply in a thread the bot has said something in
  overhear: true         GitLab, Jira: hears every issue opened and every public comment
  projects: [a/b]        GitLab, Jira: the projects it reads
  group: a               GitLab: every project of a group, with one ask
  settle: 2m             GitLab, Jira: hears an opened issue once nobody has changed it for 2 minutes; 0s by default

A message heard by `overhear` that does not name the bot has
`unaddressed: true`, which the starting routers drop. The hosts are values:
`GITLAB_SITE` and `JIRA_SITE`, each a host name such as `gitlab.example.com`,
and `JIRA_EMAIL`, the account Jira's token belongs to.

A message
---------

A message is one mapping, the same from every service.

  service        slack, telegram, gitlab or jira
  place          where it was said: dm or #channel on Slack, dm on Telegram, the project's path on GitLab, its key on Jira
  chat           the thread it belongs to
  user           the sender's ID on the service
  name, email    the sender's name, and their email where the service gives one
  text           what was said, in Markdown; Slack, GitLab and Jira take out the bot's name
  history        a blob of the thread before the message, a list of { line, attachments }, oldest first
  complete       true when history holds the whole thread
  attachments    the files sent with it, each { name, type, size, id }, and absent with none
  unaddressed    true for a message that does not name the bot
  own            true for the bot's own comment, on GitLab
  change         what changed: reaction on Slack; closed, reopened, labels, milestone or assignees on GitLab
  at             on Slack, the message's time, by which conversations/replies reads what came before it
  answers        on Telegram, the message a reply answers
  later          on a reminder, the minutes it waited; its text is the agent's note

  Telegram    chat: the chat's ID
  Slack       chat: the conversation, with /thread in a thread; a channel's message outside a thread starts its own
  GitLab      chat: project#iid
  Jira        chat: the issue's key

- `history` holds at most 20 entries and 8000 characters, and on Jira the issue and its latest 50 public comments. It is an empty list when nothing came before.
- A Slack reaction's text is the emoji, such as `:eyes:`, its `at` the message reacted to, and its history the thread before the reaction, that message included.
- A GitLab change's text says what changed, such as `labels +bug`, and an opened issue is a message whose text is its title and description.
- An answer holds `service`, `question`, the key its button or line holds, `user`, `name`, `email` and `choice`, on Telegram `tap`, and on Jira `chat`, the issue it was written on. A stop holds `service`, `place`, `chat`, `user`, `name` and `email`.

Telegram's Bot API keeps no history a bot can read, so Telegram's listener
keeps the person's messages it heard, never the bot's replies. `complete` says
it heard the chat's /start and dropped none of them since. A new run of the
listener starts with no history.

  each chat                at most 20 entries and 8000 bytes, but always its latest entry
  all chats                at most 64 KiB, a quarter of what Corbie takes as a job's input or result
  a chat quiet for a day   dropped

A message's files are these.

  Telegram    its photo, document, audio, voice, video or animation; each item of an album is its own message
  Slack       the files Slack keeps, which the bot reads with the scope files:read
  GitLab      each /uploads/ link in the comment or issue, its type from its name and no size
  Jira        the issue's files the comment names; an opened issue's, but one only a restricted comment names

The conversation
----------------

The conversation is the project's own `conversation.yaml`, a keyed
statechart: one run for each person in each thread. It answers in turns, and
each turn is a flow it runs as a child, whose stages are written in the file.

1. `asker` calls `people/find` with the first message's service, user, name and email.
2. `thread` turns the first message's history into text, and `format` says how to write for its service.
3. A status stage shows `Working...` under a Slack thread, or "typing" on Telegram.
4. `files` downloads every message's files with the bot's `files/get`, when there are any.
5. `answer` calls `agents/assistant`.
6. A second child run clears Slack's status, and posts the reply with the bot's `chat/post`.

- Messages that come during a turn are kept, and the next turn answers all of them, oldest first. The run keeps at most 100, and drops the 101st.
- A turn's thread is the history of its first message. What others wrote between that turn's messages is not shown.
- Each message added costs a job, and each kept message costs one more as the next turn starts.
- Each person's turns are their own, checked against their own scopes. Two people in one thread have two runs, which may answer at once, and see each other's messages only in the history.
- The agent's file is read for each turn, so a changed agent answers the next turn. A changed `conversation.yaml` lets the runs under way finish with the machines they started with.
- A run with no message for a day ends, and the next message starts a new one.
- A status that fails does not fail the turn, and a post that fails clears Slack's status all the same.
- When a turn fails, for any reason, the conversation posts a fixed text, `That could not be answered.`, or `This bot has no agent yet.` when there is no `agents/assistant.yaml`. The error is in the turn's record.
- After a failed turn, or a reply whose post failed, the next turn starts a new conversation with the agent.

A filter for messages the router sends marked `unaddressed`, and a redactor
for what is posted outside a direct message, are stages the project adds, as
`corbie rook manual rook-project` shows under Common changes.

  a conversation        the service, the place and the first line, as slack #help: …
  a turn                its messages' texts
  an agent answering    the asker's name and what they said
  a reply               its first line, or no reply
  an approval           Approve and the tools held
  a question            the first line of what is asked, after the issue on GitLab and Jira
  a listener            Slack listener, Telegram listener, GitLab listener, Jira listener

These are the runs' titles, as `corbie ui` lists them.

Stopping an answer
------------------

A person stops what their agent is doing with `/stop` on Telegram, or with the
stop button Slack shows under a thread while the bot works there.

1. The listener sends `stop` to the router, which sends it to the person's own conversation.
2. The conversation leaves the turn, which cancels the agent's run, its tools' runs, and any approval and question they wait on.
3. The conversation posts `Stopped.`, and answers the next message with the conversation as it was before the stopped one.

- A stop goes only to the sender's own conversation, so nobody can stop another person's agent.
- A stop that comes while a message is added cancels the turn as it starts. A stop with no turn coming is dropped.
- A Slack direct message outside a thread shows no status, so it has no stop button.
- A question that is cancelled keeps its buttons. A press on one is noted as undelivered in the record of its run of `answers`, and runs nothing.

The agent
---------

An agent is any machine at `agents/assistant`. The conversation calls it with
this input, and reads `reply` and `conversation` from its output. An agent of
type agent includes `.rook/agent.yaml`, which gives it this input, the prompt
and `receive: [conversation]`, and names no model.

  messages        this turn's messages, oldest first, each as the listener sent it
  thread          the thread before the first of them, as text
  attachments     the messages' files, each with file, its contents as a blob
  medium          the service the reply is shown on
  format          how to write for that service, which the system text holds as ${input.format}
  asker           { name, email, scopes } of the person, from the lookup
  conversation    the conversation so far, or nothing
  post            the bot's chat/post for the service, which the tool progress calls
  back            the conversation's run, { at, key }, which the tool later returns to

  reply           the conversation posts it; an empty reply, or none, posts nothing
  conversation    goes to the next turn

- The prompt puts the thread in `<thread>` tags, which a thread's words cannot close.
- The model is shown each PNG, JPEG, GIF or WebP image of at most 5 MiB, and each PDF, when its service takes them. Any other file is a blob, which the agent reads with Corbie's blob tools.
- A flow or a statechart with the same input and output answers with no model.
- The prompt gives a reminder's note as the agent's own reminder, which the person did not write.

`.rook/agent.yaml` gives the agent two tools.

  progress   { text }: posts in the person's chat at once, before the reply; offered when the conversation gives post
  later      { minutes, note }: after 1 to 1440 minutes, the note comes back as a message; offered when the conversation gives back

A reminder whose conversation ended in the meantime starts it again, with no
earlier turns, so the note says in full what to do. At most 20 reminders wait
at once in a project, and a stop does not cancel one.

An agent's toolkits are listed under `toolkits:`, each with a `when:` on the
agent's input, so only a person whose scopes allow it is offered one. A tool
written `call: <location>` calls a machine of the tree, taking its description
and arguments from that machine, and fixing any of its input. `corbie rook
manual rook-project` shows an agent and its toolkit under Add an agent.

The lookup
----------

The lookup at `people/find` takes `{ service, user, name, email }` and gives
`{ name, email, scopes }`. Rook's reads `people/scopes.yaml`, where each row
is an email with a name and scopes, and matches the email, ignoring case.

- An email the table does not hold, or none, gives no scopes and the name the service gave.
- A row that is not `{ name, scopes }` fails every lookup, naming the row.
- Telegram gives no email, so a person on Telegram holds no scope unless a lookup of the project's own finds them by `user`, their Telegram ID.
- A lookup that asks a directory, such as Entra, takes and gives the same, and replaces `people/find.yaml` with no other change.

Asking a person
---------------

A question is a run of the bot's placed `chat/ask`, which includes
`.rook/chat/ask.yaml`, the same statechart on every service. A machine calls
it with `{ in, text, choices, approvers, asker, within, ballot }`, and it
gives `{ choice, by }`.

1. It makes its key, 12 random letters and digits, and sends `open` to the run of `answers` at that key.
2. It calls the service's `chat/show` to post `text` in `in` with a button for each of `choices`, each holding the key.
3. For each press its router sends to `answers` at that key, it runs `.rook/shared/press.yaml`, which calls the lookup for the presser. A choice is matched in any case.
4. A press from someone whose scopes lack `approvers`, or whose email is `asker`, is refused. `chat/show` tells the presser why, and the buttons stay.
5. The first press that counts ends it with `{ choice, by }`, and `chat/show` shows who answered in place of the buttons. With none within `within`, by default 7d, it ends with `{ choice: no }`.

A button holds the key, and not the question's run ID, which grows with the
client's name: Telegram keeps 64 bytes of a button. The run of `answers` ends
when the question sends it `shut`, as it takes no more answers, or `within`
after `open`.

A service's `chat/show` is the one part that differs: a flow of one job that
runs the service's script, with the service's `allow:`.

  Slack       tells a refused presser in a message only they see, in the question's thread
  Telegram    tells a refused presser in an alert, or in their own chat with the bot; cuts a question over 4096 characters in its middle
  GitLab      asks in a comment on the issue; a comment that is only a choice is the answer
  Jira        shows a line for each choice, <choice> <key>; a comment on the question's issue that holds only such a line is the answer

The placed file fixes three fields of the input with `const:` and `default:`,
so no caller gives them, as the file with deploys added below shows.

  router   the router, grouse/slack/grouse: answers drops an answer whose sender, event.from, is any other location
  lookup   the lookup the question calls for who pressed, people/find
  show     the service's chat/show, grouse/slack/chat/show

`ballot` is the address `{ at, key }` of a run of `ballot`, which lets one
approval ask in several places at once.

1. Each question sends the ballot `opened` once it has posted.
2. The first whose press counts sends it `settled`, `{ choice, by, where }`, `where` naming the service, such as Slack.
3. The ballot sends each other question `close`, with the same data, including one that posts later.
4. That question shows "<by> said <choice> on <where>." in place of its buttons, and ends with `{ choice, by, elsewhere: true }`.

A later `settled` is dropped. The ballot ends when its approval sends it
`over`, or a day after it settled.

Rook's approval, `.rook/approval.yaml`, is an ask, which an agent or another
machine names under `ask:`. It asks the question in every place of `ask` at
once, with yes and no, naming the asker by email and each held call with its
arguments, and quoting what was asked and what the agent said. An argument of
one line over 300 characters is shown as its first and last 150 characters,
with its length. It gives `{ approved, note }`.

  ask         the places, each { at, in }: the question's location, such as grouse/slack/chat/ask, and where it is posted there: a channel, a thread or a chat
  approvers   the scope a press needs to count
  within      how long it waits; 7d by default, and no press in time is no
  asker       the email of the person who asked, shown in the question, whose own press is refused; left out, they may approve their own request
  request     what was asked, shown quoted
  by          by a tool's or a toolkit's name, its own ask, approvers or within; tools of one name in two toolkits share an entry

An agent has one ask, which is shown each held call's `tool` and
`toolkit`. A held call whose tool's name, or else whose toolkit's name, is an
entry of `by` is asked about apart from the other calls, with that entry's
fields in place of the approval's. A call left with no place to ask, or no
approvers, is denied with the reason.

A machine that is no agent asks the same way: its `ask:` is the approval, and
a job marked `approve: true` waits for it. Here one run for each thread starts
the orders pipeline once someone with `deploy:approve`, who did not ask,
presses yes.

    # deploys.yaml
    statechart: deploys
    description: Starts the orders pipeline when someone writes "deploy orders".
    lifetime: keyed
    receive: [grouse/slack/grouse]
    allow: [send:grouse/gitlab/pipeline/create, send:grouse/slack/chat/post]
    ask:
      machine: .rook/approval.yaml
      input: { ask: [{ at: grouse/slack/chat/ask, in: "${input.chat}" }], approvers: "deploy:approve", within: 1h, asker: "${input.email}", request: "${input.text}" }
    initial: waiting
    states:
      waiting:
        on:
          message:
            - { go: deploying, when: "${event.data.text === 'deploy orders'}" }
            - over
      deploying:
        job:
          call: { at: grouse/gitlab/pipeline/create }
          input: { project: group/orders, ref: main }
          approve: true
        on: { done: telling, failed: telling }
      telling:
        job:
          call: { at: grouse/slack/chat/post }
          input: { in: "${input.chat}", text: "${event.name === 'done' ? 'Pipeline started.' : 'The pipeline did not start.'}" }
        on: { done: over, failed: over }
      over: { end: done }

    # grouse/gitlab/pipeline/create.yaml
    include: .rook/gitlab/pipeline/create.yaml

    # grouse/slack/chat/ask.yaml, with deploys added
    include: .rook/chat/ask.yaml
    receive: [answers, agents/*, ballot, deploys]
    input:
      properties:
        router: { const: grouse/slack/grouse, default: grouse/slack/grouse }
        lookup: { const: people/find, default: people/find }
        show: { const: grouse/slack/chat/show, default: grouse/slack/chat/show }

- The approval runs at the asking machine's location, so the question's `receive:` lists that location, or the call is refused.
- The approval gives each question the ballot `{ at: ballot, key: <the approval's run ID>/<n> }`, `<n>` numbering the calls it asks about apart. Its answer is the first that counts in any place; a place whose question fails leaves the others asking.
- A held call that is not approved fails as `denied`, which goes back to a model as the tool's result.
- The router sends the thread's messages to `deploys`, as `corbie rook manual rook-project` shows under Common changes.

Rook's calls
------------

Each of Rook's calls has a `description:` and an `input:`, so a toolkit's
tool can name it with `call:`. A project places one with a file of one line,
as `grouse/gitlab/pipeline/create.yaml` above, and any machine of the project
may call it with `send:` for it in its `allow:`.

  chat/post                    { in, text }: posts Markdown, which each service writes in its own form
  chat/ask                     the question, as under Asking a person
  slack assistant/status       { in, text }: an empty text clears the status
  telegram chat/status         { in, text }: "typing" for five seconds
  files/get, attachment/get    { attachments }: each with file, its contents as a blob; at most 32 MiB, or 20 MB on Telegram
  slack files/upload           { in, name, file }: in is a conversation, a channel's #name or a member ID
  telegram files/send          { in, name, file }
  slack conversations/replies  { in, at }: the thread before a message
  GitLab's others              issues/read, issues/notes/create, issues/notes/list, uploads/create, repository/files/read, repository/commits/create, pipeline/create: GitLab's own input, such as project and iid
  Jira's others                issue/comment/create, issue/comment/list, issue/attachments/create: input such as issue, the issue's key

    # schedules/evening.yaml
    statechart: evening
    description: Says the day is over in a Telegram chat at 18:00.
    lifetime: singleton
    allow: [send:grouse/telegram/chat/post]
    initial: waiting
    states:
      waiting:
        timers: { due: "18:00 Europe/London" }
        on: { due: telling }
      telling:
        job: { call: { at: grouse/telegram/chat/post }, input: { in: "123456789", text: The day is over. } }
        on: { done: waiting, failed: waiting }

`in` on Telegram is a chat's ID, and the bot can post only in a chat where
the person wrote to it first.

Filters
-------

A filter says whether a message that does not name the bot is for it, and
gives `{ reply: { answer } }`. A project places one and adds a stage that
calls it to its conversation.

  .rook/filters/words.yaml   { text, words }: true when the text holds one of the words, ignoring case
  .rook/filters/model.yaml   included by an agent with a small model: { text, name, thread }; it says no when unsure

Charts, layouts and diagrams
----------------------------

An agent learns what its service shows from `${input.format}`: layouts only on
Slack, diagrams only on GitLab, and no tables on Telegram.

A chart is a fenced block marked `chart`, holding one JSON object. Slack draws
it, two to a message, and every other service writes it as a table. So does
Slack, for a chart outside its limits.

    ```chart
    {"type": "bar", "title": "Tickets", "labels": ["Jan", "Feb"], "series": [{"name": "Email", "values": [140, 165]}], "x": "Month", "y": "Tickets"}
    ```

  type       bar, line, area or pie; a pie takes the first series
  title      at most 50 characters on Slack
  labels     the categories; on Slack all different, at most 20, or 12 for a pie, each at most 20 characters
  series     each a name and one number in values for each label; on Slack at most 12, names different and at most 20 characters
  x, y       the names of the axes, at most 50 characters on Slack

- A layout is a fenced block marked `blocks`, holding a JSON list of Slack's Block Kit blocks. Slack posts them, at most 50 to a message, with every `action_id` and each button's `value` taken out, so a button in a layout only opens its `url`.
- Every other service, and Slack for a layout it refuses, writes the layout's text.
- GitLab draws a fenced block marked `mermaid` as a diagram, and every other service shows it as it was written.

Who may do what
---------------

1. Corbie's permissions apply first. A job may do only what its `allow:` says, within the ceilings, and a secret goes only to the host it is bound to.
2. A service's secrets are set at `/my-bot/<bot>/<service>`, so the agent's run, at `/my-bot/agents/assistant`, cannot read them.
3. An agent is allowed only its model. Its model calls the agent's own tools, the tools of each toolkit it was offered and opened, and Corbie's tools that read blobs.
4. A toolkit is offered only when its `when:` holds on the agent's input, which holds the asker's scopes from the lookup.
5. A tool marked `approve: true` waits for the agent's ask, which counts a press only from someone whose scopes hold its approvers.

What Rook does not defend against
---------------------------------

- A tool that sends to a destination its arguments choose can send whatever the run read. Give it `approve: true`.
- Text a tool returns, such as an issue or a web page, and a thread's history, can tell the model to do things. Give each tool that changes something `approve: true`.
- A redactor cleans only what is posted. The model sees every tool's whole result, and so does that person's next turn.
- Rook takes a message's sender from the service, and trusts the email the service gives. A row in `people/scopes.yaml` gives its scopes to whoever the service says holds that email.
- Slack gives the email of a person from another organisation in a Slack Connect channel as that organisation set it.
- GitLab gives a person's public email, which they choose on their account, unless the token is an administrator's. A GitLab that does not confirm emails lets a person show someone else's.
- Jira gives an email only where the person's privacy settings show it. Without one, the person holds no scope.
- Telegram gives no email, so only a project's own lookup that finds a person by their Telegram ID gives them a scope.
- The question refuses an asker's own press by email. When the lookup gives no email for the asker or the presser, a person's own press is not refused.
- Rook's GitLab listener assumes that a change of labels or milestone moves the issue's `updated_at`, which GitLab's documentation does not say and which is not yet checked. If it does not, the change is heard only with the issue's next other change.
- A person who sends more than 100 messages during one turn loses the rest.
- Anyone who can change the directory can change every rule above but the first. Guard it by review in git.
