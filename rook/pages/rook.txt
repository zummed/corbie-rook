Rook: ready-made Corbie machines for a bot that answers people on Telegram, Slack, GitLab issues and Jira issues.

A person has asked you to set up or change a Rook project. `corbie rook init`
writes Rook's machines into the project's `.rook/`, and the project's own
files say where each message goes, who someone is, and what each agent can do.

Read a page with the manual tool of corbie mcp, or in a shell with `corbie
rook manual <page>` and `corbie manual <page>`. Run a command with the corbie
tool, or in a shell. Either runs in the project, so the project is `.`.

Before you change a project
---------------------------

1. Read `corbie rook manual rook-project` and `corbie rook manual
   rook-design`. They give the project's files, what to change for what the
   person wants, and what each machine takes and gives.
2. Read the project's files, and the notes in its `AGENTS.md`. Read
   `.rook/`, and change nothing there, since `corbie rook init` rewrites it.
3. Read `corbie manual definitions`, `corbie manual agent`, `corbie manual
   scripts` and `corbie manual permissions`, and the page of each machine
   type and plugin you use, before you write a machine. The manual gives
   every field and every call, so never guess one.

A new project
-------------

`corbie rook init` starts a project with no agent, so the bot answers nobody.
Before you write anything, ask the person:

- who the bot is for, and each person's email and what they may do, for `people/scopes.yaml`
- what the bot should do first, which gives the agent's toolkits and the machines their tools call
- who says yes to a tool that changes something, and where the question is posted
- which model the agent uses, and the name of the secret that holds its key; an agent may be a machine with no model

A person on Telegram has no email, so they hold no scope unless the project's
lookup finds them by their Telegram ID. Then add the agent as `corbie rook
manual rook-project` says under Add an agent, and give the person the secrets
and values `init` named.

While you write
---------------

- Choose each change with the table under Common changes in `corbie rook manual rook-project`.
- Name scopes as `<toolkit>:<what>`, such as `orders:read` and `orders:approve`, and give a toolkit a `when:` on the asker's scopes on its entry in the agent's file.
- Write a tool as `call: <location>` of a machine the project places or writes, with `input:` fixing what the model must not choose, and `approve: true` when it changes something. A schedule, another machine or a client can then run the same machine without the agent.
- Give an agent with a held tool an `ask:` that runs `.rook/approval.yaml`, with `asker: "${input.asker.email}"`, so the approvers see who asked and nobody approves their own request, a `request:` that marks a reminder's note as the bot's, and in `ask:` each place to ask, as `{ at, in }`, as `corbie rook manual rook-project` shows. To ask other people about a toolkit or a tool, give it an entry of `by:`.
- Place a call of Rook's with a file of one line under `<bot>/<service>/`, as `include: .rook/gitlab/pipeline/create.yaml`.
- Add a location that calls the bot's `chat/ask` to the `receive:` of its placed file, or the call is refused.
- An agent that includes `.rook/agent.yaml` takes calls only from `conversation`. When another conversation calls it, write `receive:` in the agent naming both.
- A router and Rook's listener write `receive: []`, so the router takes events only from its listener. Keep it: a machine sends nothing to a router.
- Give a statechart a router sends to `receive:` naming that router, and a statechart run as a child its own `receive:`: a child run is addressed by its ID at its parent's location.
- Give each job only the permissions it needs, in its `allow:` list.
- Never ask for a secret's value or write one in a file. Give the person the command `corbie controller secret set <NAME> --at /<project>/<location>`, where `<project>` is the project directory's name.
- For Slack, give the person the steps and the manifest under The Slack app in `corbie rook manual rook-project`, with their name and description.
- Add a line under Notes in the project's `AGENTS.md` for what a later reader needs that the files do not say, such as what a toolkit is for.

After you change a project
--------------------------

1. Run each script you wrote that needs no secret with `corbie test`.
2. Run `corbie test .`, which reads every machine and starts nothing.
3. Tell the person each file you added or changed, by Rook's name for it
   (agent, toolkit, tool, scope, router, schedule), and why. Tell them what
   each job is allowed, and who each toolkit is offered to.
4. Give the person `corbie run submit .`, to run where the bot runs. Run it
   yourself only when the person asks: a second copy of a router takes the
   first one's messages.
5. Tell the person that `corbie ui`, started in the project, shows each run,
   draws each machine, and lists each toolkit with its tools that have
   `approve: true`.

After `corbie rook init` updates a project, it names the project's files that
are not as this version starts a project. Compare each with its version in
`corbie rook manual rook-starter`, and tell the person what differs and what
each difference does. Change nothing until they say which to take.

Reference
---------

  corbie rook manual rook-design     the runs that answer a message, what each machine takes and gives, and who may do what
