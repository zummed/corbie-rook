Rook design: the runs that answer a message, what each block takes and gives, and who may do what.

Rook is ready-made Corbie machines in a project's `.rook/`. The project's own
files fill five slots, and its own machines use Rook's blocks as jobs.

What runs where
---------------

`corbie run submit .` records the project as one tree: `/my-bot` for a
directory named `my-bot`. A file with a type line has a location, its path
under `/my-bot` without `.yaml`. A file without one is a piece, which a
machine includes.

  /my-bot/bridges/<bridge>                 singleton: the bridge, and its listener as a child run
  /my-bot/.rook/blocks/chat                keyed <bridge>:<chat>: one thread
  /my-bot/.rook/blocks/conversation        keyed <bridge>:<chat>:<agent>: one thread with one agent
  /my-bot/agents/<agent>                   called by a conversation for each message
  /my-bot/lookup                           called for who someone is, and how to reach them
  /my-bot/attend                           called for a message that does not name the bot, when the project has attend.yaml
  /my-bot/review                           called for a held call, when the project has review.yaml
  /my-bot/.rook/blocks/ask                 called: one question, waiting for a tap
  /my-bot/.rook/bridges/<bridge>/<action>  called: say, send, status, history, attachments, ask, close

Every other block runs as a child of the run that uses it, at that run's
location. A run uses the secrets and values set at its location or above, so
`init` prints the commands that set them at `/my-bot`.

How a message is answered
-------------------------

1. The listener hears a message, and sends `message` to `.rook/blocks/chat` with the key `<bridge>:<chat>`.
2. The chat runs `who.yaml`, which calls `lookup` and reads `rules.yaml` for the person and the agent they get there.
3. The chat reads the thread before the message, and calls `attend` for a message that does not name the bot.
4. The chat sends `message` to `.rook/blocks/conversation` with the key `<bridge>:<chat>:<agent>`.
5. The conversation calls `agents/<agent>`, and says the reply where the message came from.

A send to a key with no running run starts one, with the event's data as its
input. A chat and a conversation each take one message at a time, in the order
they were sent.

Following a message
-------------------

Each send and each call names, in the sender's record, the run it went to,
and that run names the run that started it. These commands show them.

  corbie run ls --all              each run, its location, its key, and the run it is a child of
  corbie run show <id>             the run, with started by: the run whose send or call started it
  corbie run show <id> --record    each step of the run and its child runs, and each send or call with the run it went to

1. In the bridge's record, each message is a send to `/my-bot/.rook/blocks/chat#<bridge>:<chat>`, naming the chat's run.
2. In the chat's record, `who` gives `rule`, the entry of `rules.yaml` that chose the agent, and the send names the conversation's run.
3. In the conversation's record, the call to `/my-bot/agents/<agent>` names the agent's run.
4. The agent's record shows each tool as a job, a held tool as `hold <tool> for the ask`, and its part's approval as a child run, whose call to `/my-bot/.rook/blocks/ask` names the question's run.
5. The question's record names the run of the bridge's ask that posted it.

Record lines are shown without their time and run, and a name in angle
brackets, such as `<chat>`, stands for a run's ID.

    corbie run show <chat> --record
      step 2  <- done from who {"agent":"helper","groups":[],"person":"alice","rule":{"for":["alice"],"name":"helper"}}
      step 2  -> send message to /my-bot/.rook/blocks/conversation#telegram:1:helper · started <conversation>
    corbie run show <conversation> --record
      step 3  -> job answer: a call to /my-bot/agents/helper, <agent>
    corbie run show <agent> --record
      step 6  -> hold tell for the ask
      step 6  -> job ask: a machine, <approval>
      step 2  -> job person: a call to /my-bot/.rook/blocks/ask, <question>
    corbie run show <question> --record
      step 1  -> job first: a call to /my-bot/.rook/bridges/telegram/ask, <ask>

Who may talk to whom
--------------------

Rook's files write no `receive:`, so each location takes sends and calls from
every location of the project and from the client that submitted it. Every
other tree and client is refused. A sender needs `send:` for the location in
its `allow:`.

  .rook/bridges/<bridge>/listen.yaml   send:.rook/blocks/chat, and send:.rook/blocks/ask on Telegram and Slack
  .rook/blocks/chat.yaml               send:.rook/blocks/conversation, and send:attend in its child run route
  .rook/blocks/conversation.yaml       send:agents/** in its child run message
  .rook/blocks/who.yaml, tell.yaml     send:lookup
  .rook/blocks/approval.yaml           send:review, send:.rook/blocks/ask
  .rook/blocks/ask.yaml                send:lookup, send:.rook/bridges/slack/ask
  .rook/blocks/say.yaml and the rest   send: for the action of every bridge, as send:.rook/bridges/*/say

- The client that submitted the project may send to and call every location in it, with no `send:`: `corbie run submit /my-bot/agents/helper --input '…'` runs one agent alone.
- A gateway is a client, so a gateway whose client submitted the project can call any of its locations with any input. Submit the project from a client no gateway uses.
- A file that takes sends from another tree or client writes `receive:`, as `corbie manual machines-together` says.

Five slots
----------

  Bridges     bridges/<name>.yaml: where messages come in
  People      lookup.yaml: who someone is, their groups, and how they are reached
  Attend      attend.yaml, which a project may leave out: whether a message heard by overhear is for the bot
  Rules       rules.yaml: which agent each person gets where
  Parts       agents/, parts/, and review.yaml, which a project may leave out: what the agents can do, and who approves it

`.rook/bridges/` and `.rook/people/` hold Rook's own machines for bridges and
people, and `.rook/attend/` and `.rook/review/` the pieces an agent at
`attend.yaml` or `review.yaml` includes. A machine of the project's can take
the place of any of them.

What init writes
----------------

`corbie rook init` rewrites `.rook/`, with the machines of each bridge whose
file is in `bridges/`. The first time, it writes the starting files, which
hold no agent and no part. After that it writes only a file the project lacks:
one a machine in `.rook/` reads by name, `AGENTS.md`, `CLAUDE.md`,
`.mcp.json`, or the file of a bridge named with `--bridges`.

The machines in `.rook/` read `rules.yaml`, and call `lookup`, `attend`,
`review` and `agents/<agent>`. `.rook/people/file.js` reads `people.yaml`.

  bridges/<name>/listen.yaml           a piece: the listener, which the bridge's file includes
  bridges/<name>/say.yaml              says a text; every bridge has one
  bridges/<name>/send.yaml             sends a file; every bridge has one
  bridges/<name>/attachments.yaml      downloads a message's files; every bridge has one
  bridges/<name>/history.yaml          reads a thread; Slack, GitLab and Jira
  bridges/<name>/ask.yaml, close.yaml  asks with buttons, and shows the answer; Telegram and Slack
  bridges/<name>/status.yaml           shows a status; Telegram and Slack
  bridges/gitlab/api.js, jira/api.js   the service's REST API, for the bridge and a part's script
  blocks/chat.yaml                     one thread: who a message is from, and whether to answer it
  blocks/conversation.yaml             one thread with one agent: calls the agent, and says its reply
  blocks/who.yaml, who.js              the person a message is from, and the agent they get there
  blocks/say.yaml, tell.yaml           says a text at an address, or to a person
  blocks/send.yaml, file.js            sends a file at an address, for the tool send
  blocks/attachments.yaml              downloads a message's files to answer it
  blocks/types.js                      a file's media type by its name
  blocks/ask.yaml, close.yaml          asks people and gives their answer, then shows it where it asked
  blocks/direct.yaml, fail.js          calls a bridge's ask or say for a person, on their first bridge the project runs
  blocks/status.yaml                   shows a status at an address
  blocks/history.yaml, thread.js       what a thread held before a message
  blocks/form.yaml                     a form in the asker's Slack conversation, for the tool form
  blocks/approval.yaml, held.js        a part's ask: the review, then the part's people
  blocks/rich.js                       draws charts and layouts on Slack, and writes them as text elsewhere
  blocks/format.js                     how to write for each bridge, given to an agent as format
  agents/base.yaml                     a piece: what every agent answering a message takes from Rook
  attend/agent.yaml                    a piece: the prompt and reply of an agent at attend.yaml
  review/agent.yaml                    a piece: the prompt and reply of an agent at review.yaml
  people/file.js                       reads people.yaml, for lookup.yaml
  AGENTS.md                            the page corbie rook manual rook, for a model

A bridge
--------

A bridge's file is a singleton: `corbie run submit .` starts it, and it runs
while the file is there. Its listener is a child run, whose machine is the
piece `.rook/bridges/<name>/listen.yaml`.

    # bridges/gitlab.yaml
    flow: gitlab-bridge
    title: GitLab bridge
    lifetime: singleton
    stages:
      listen:
        job:
          machine: { statechart: gitlab-listen, include: .rook/bridges/gitlab/listen.yaml }
          restart: { when: always }
          input: { projects: [group/project] }

- `restart: { when: always }` starts the listener again if it ends. After a failed read, a listener waits in its state `resting`, then reads again.
- A message or a tap that a listener can never handle, such as one in a Slack channel whose name the bot cannot read, is logged and skipped.
- After any other failure, such as a network error, Slack sends the message again and Telegram gives it again, and it is answered once.
- The hosts are values: `GITLAB_SITE` and `JIRA_SITE`, each a host name such as `gitlab.example.com` with no `https://`, and `JIRA_EMAIL`, the account Jira's token belongs to.
- A listener reads a value when it starts. After changing one, run `corbie run cancel /my-bot/bridges/<name>`, then `corbie run submit .`.
- A bridge the project does not run has no machines in `.rook/`, and needs no secret.

  Telegram    hears a direct message, except /start, and logs a message in a group
  Slack       hears a direct message, or a message that names the bot, over Socket Mode
  GitLab      reads every 30 seconds each issue opened or commented on that names the bot
  Jira        reads every 30 seconds each issue opened or commented on that names the bot

The Telegram and Slack listeners send each tap on a question as `answer`, to
the run whose ID the button holds.

These settings go in a listener's input:

  overhear: true    Slack: hears a reply in a thread the bot has said something in
  overhear: true    GitLab, Jira: hears every issue opened and every public comment
  settle: 2m        GitLab, Jira: hears an opened issue once nobody has changed it for 2 minutes; 0s by default

A message heard by `overhear` that does not name the bot has
`unaddressed: true`. A comment made on an issue that is still settling is in the
issue's history. When the issue does not name the bot and such a comment does,
the latest such comment is heard in the issue's place. Telegram's listener
takes no input, and fails naming any it is given.

A message
---------

A message is one mapping, the same from every bridge, and every block takes it
or a part of it.

  bridge         telegram, slack, gitlab or jira
  chat           the thread it belongs to
  from           the sender's id on the bridge
  text           what was said; Slack, GitLab and Jira take out the bot's name
  place          where it was said, as rules.yaml names places
  at             the message's id on the service, where a bridge reads a thread
  answers        the message a reply answers, on Telegram
  unaddressed    true for a message that does not name the bot, and absent otherwise
  attachments    the files sent with it, each { name, type, size, id }, and absent with none

  Telegram    chat: the chat                                         place: dm
  Slack       chat: the conversation and thread                      place: dm, or #channel
  GitLab      chat: project#iid                                      place: the project
  Jira        chat: the issue's key                                  place: the project's key

In a channel, each message that is not in a thread starts its own Slack
thread. An answer holds `bridge`, `question`, `from` and `choice`, and on
Slack `values`, the form's fields by name.

A message's files are these.

  Telegram    its photo, document, audio, voice, video or animation; each item of an album is its own message
  Slack       the files Slack keeps, which the bot reads with the scope files:read
  GitLab      each /uploads/ link in the comment or issue, its type from its name and no size
  Jira        the issue's files the comment names; an opened issue's, but one only a restricted comment names

A conversation
--------------

A conversation is a run of `conversation.yaml`, for one thread and one agent.
It answers its messages one at a time, each with a new run of the agent given
the conversation so far.

- Two people in one thread who get two agents have two conversations. An agent is never given another agent's conversation or tool results.
- Everyone in a thread who gets the same agent shares its one conversation, with each tool call and result. A tool that reads one person's data belongs to an agent for a place only that person reads.
- Every agent in a thread is given the thread's history and its earlier files, which everyone in the thread can read.
- A chat or a conversation quiet for a day ends, and the next message starts a new one.
- The agent's file is read for each message, so a changed agent answers the next message of a conversation under way.
- A change to `chat.yaml` or a file it reads, such as `rules.yaml`, cancels the chats, and each thread's next message starts a new one.
- A change to `conversation.yaml` lets the conversations under way finish with the machines they started with.
- On Slack, GitLab and Jira, each message has the thread or issue read as it was before the message: the latest 20 entries, at most 8000 characters, from the first 1000 of a Slack thread. Telegram keeps nothing a bot can read.
- A new conversation is given that history's text, and every message its files. The history holds what was said, and no tool calls or results. When the read fails, the message is answered with no history.
- The history's files go to the agent as `earlier`: the latest 20, without their contents. On Jira they are the issue's files, but one a restricted comment names.
- Rook reads nothing for a person with no agent.
- A message's own files are downloaded only to answer it, and an earlier file only when the agent looks at it with the tool `look`. Each is at most 32 MiB, or 20 MB on Telegram.
- With files, the agent's prompt is `{ message, attachments, earlier }`. Each file in `attachments` holds its contents as a blob.
- The model is shown each PNG, JPEG, GIF or WebP image of at most 5 MiB, and each PDF, when its service takes them. Any other file is a handle, and the agent reads a text file with Corbie's blob tools.
- When a download fails, the agent gets each file as the message holds it, with no contents.
- While an agent works, the conversation shows `Working on it.` under a Slack thread and "typing" on Telegram. A reply clears it on Slack, and so does an answer that says nothing.
- A conversation waits up to seven days for an approval, and up to an hour for a form.
- When an answer fails, the conversation says `That could not be answered. Ask again in a while.`, and answers the next message with no conversation so far and with what the thread held before it.
- When `who.yaml` fails for a message that names the bot, as for an entry of `rules.yaml` with no `for:`, the chat says `That could not be answered. Ask again in a while.`
- When someone with no agent names the bot, the chat says `This bot answers only the people it belongs to.`, or `This bot does not answer you here.` to someone `lookup.yaml` knows.

  a chat                  where it is and the first line said: #help: …, dm: …, #7 … on GitLab, OPS-1 … on Jira
  a conversation          the agent's name, where it is and the first line said: helper in #help: …
  a message               all that was said, or the names of its files
  an agent answering      the asker's name and what they said, or the names of its files
  a question, a form      the first line of what is asked
  an approval             Approve, the tools held, and the asker's latest message
  a bridge, its listener  Slack bridge, Slack listener

These are the runs' titles, as `corbie ui` lists them.

Your machines
-------------

An agent is any machine at `agents/<agent>`. The conversation calls it with
this input, and reads `reply` and `conversation` from its output. An agent of
type agent includes `.rook/agents/base.yaml`, and a flow or a statechart with
the same input and output answers with no model.

  said            the text of the message
  asker           the person's name, from lookup.yaml
  request         the conversation's last five messages, each as asker: text
  home            the project's directory
  address         where the message came from
  history         what the thread held before this message, for a new conversation on Slack, GitLab or Jira
  attachments     its files, each as the message holds it with file, its contents
  earlier         the files earlier in the thread, without their contents
  conversation    what the last answer gave, or nothing
  format          how to write for the message's bridge: Markdown or not, and how to write a chart, a layout or a diagram

  reply           the conversation says it at the address; an empty reply or no output says nothing
  conversation    goes to the next answer in this conversation

Any machine can run these blocks as jobs, as `machine:
.rook/blocks/tell.yaml`. A path in a machine is read from the project's top
directory, and a path starting `./` from the machine's own directory.

  .rook/blocks/tell.yaml      person, text: says a text to a person named in lookup.yaml, on their first bridge the project runs
  .rook/blocks/say.yaml       address, text: says a text at an address
  .rook/blocks/send.yaml      address, name, file or text: sends a blob, or a text as a file, at an address
  .rook/blocks/status.yaml    address, text: shows a status under a Slack thread or as "typing" on Telegram

    # schedules/evening.yaml
    statechart: evening
    lifetime: singleton
    initial: waiting
    states:
      waiting:
        timers: { due: "18:00 Europe/London" }
        on: { due: telling }
      telling:
        job: { machine: .rook/blocks/tell.yaml, input: { person: alice, text: The day is over. } }
        on: { done: waiting, failed: waiting }

- An address is a mapping, `{ bridge, id }`, with `answers` and `at` where a bridge uses them. A block takes the whole mapping.
- On Slack, an address's `id` may be a channel's `#name`.
- The chat gives the address of each message. `lookup` with `do: reach` gives each person's bridges that reach a person directly, in their entry's order, with their ids.
- On `status.yaml`, an empty text clears the status on Slack, and Telegram's "typing" ends by itself. A status that fails gives `{ shown: false }`, and does not fail.

A reply to a text goes to the chat as a new message. The agent that answers it
sees the text only when it starts a new conversation on Slack, whose history
holds it. Only a tap on a question goes back to the machine that asked.

Charts, layouts and diagrams
----------------------------

An agent learns what its bridge shows from `${input.format}`: layouts only on
Slack, diagrams only on GitLab, and no tables on Telegram.

A chart is a fenced block marked `chart`, holding one JSON object. Slack draws
it, two to a message, and every other bridge writes it as a table. So does
Slack, for a chart outside its limits.

    ```chart
    {"type": "bar", "title": "Tickets", "labels": ["Jan", "Feb"], "series": [{"name": "Email", "values": [140, 165]}], "x": "Month", "y": "Tickets"}
    ```

  type       bar, line, area or pie; a pie takes the first series
  title      at most 50 characters on Slack
  labels     the categories; on Slack all different, at most 20, or 12 for a pie, each at most 20 characters
  series     each a name and one number in values for each label; on Slack at most 12, names different and at most 20 characters, a pie's values above 0
  x, y       the names of the axes, at most 50 characters on Slack

- A layout is a fenced block marked `blocks`, holding a JSON list of Slack's Block Kit blocks. Slack posts them as they are, at most 50 to a message, and only the first 50 of one layout.
- Every other bridge, and Slack for a layout it refuses, writes the layout's text.
- GitLab draws a fenced block marked `mermaid` as a diagram, and every other bridge shows it as it was written.
- A block that does not read as a chart or a layout is left as it is written.

Attend
------

A project may write `attend.yaml`. The chat calls it for a message heard by
`overhear` that does not name the bot, with `said`, `asker`, `address` and
`history`, and answers the message only when it gives
`{ reply: { answer: true } }`.

    # attend.yaml
    agent: attend
    include: .rook/attend/agent.yaml
    model: { name: claude-haiku-5-5, secret: ANTHROPIC_KEY }
    system:
      - { include: .rook/attend/agent.yaml#system }
      - The bot answers questions about the build.

- `.rook/attend/agent.yaml` gives the input, the system text, the prompt and the reply. Its system text says no when unsure.
- A machine of the project's own can be `attend.yaml`, with the same input and output.
- With no `attend.yaml`, or one that fails, the message is not answered, and the chat's record shows the failed call.
- `attend` is called only for someone with an agent, and its `said` ends with a line naming the message's files, as `(files: error.png)`.
- A message with `unaddressed: true` never gets a refusal.

Asking a person
---------------

A question is a run at `.rook/blocks/ask`. A machine calls it, and its buttons
hold its run's ID, so a tap goes to it.

1. The question asks each person `people` names in a direct message, on the first bridge in their entry that reaches them and that the project runs, or posts in `in`.
2. A tap counts when it is on one of `choices` and `lookup` says its sender is someone `people` names, or in a group it names, on any bridge.
3. The first tap that counts is the answer. The question's messages then show who answered and the values, and lose their buttons.
4. The call gives `choice` and `person`, who answered, and `values` when the question has fields. Unanswered after `within`, it gives only `choice: no`.

    # ask-alice.yaml
    flow: ask-alice
    allow: [send:.rook/blocks/ask]
    stages:
      question:
        job:
          call: { at: .rook/blocks/ask }
          input: { people: [alice], text: "The disk is full. Clear the cache?", choices: ["yes", "no"] }
    output: ${stages.question.output.choice}

  people     people and groups to ask
  in         a Slack channel's #name, or a Slack conversation's address id; the bot must be in it
  text       what is asked
  choices    a button for each
  fields     form fields, each { name, label, kind, choices }, kind text, long, number or choice; Slack only
  within     how long to wait; 7d by default

- A machine calls the question, and never runs it as a child: a tap goes only to a run at `.rook/blocks/ask`.
- A tap on a question that has ended is noted as undelivered in the bridge's record, and starts nothing. A tap or press that names no question is logged by the listener.
- A person is asked on the first bridge in their entry that the project runs. `.rook/blocks/direct.yaml` calls each bridge's ask in turn, and goes to the next when nothing is recorded at `.rook/bridges/<bridge>/ask`.
- A person with no bridge the project runs that reaches them directly cannot be asked: the call fails, naming their bridges.
- GitLab and Jira only comment on an issue, so they ask no questions.
- The tool `form` in `.rook/agents/base.yaml` asks the person who asked, in the Slack conversation the message came from, with the buttons Send and Cancel, for an hour. On another bridge it gives a note that forms are shown only on Slack.

Parts
-----

A part is a group of tools an agent's model opens when it needs them. It is
written under `open:`, usually as a file under `parts/` that the agent
includes. Its `ask:` names who approves its held calls, so whoever writes the
part chooses them.

    # parts/messages/part.yaml
    does: Messages to the people this bot knows.
    ask: { machine: .rook/blocks/approval.yaml, input: { part: messages, people: [alice], request: "${input.request}" } }
    tools:
      tell:
        does: Say a text to a person, by their name in people.yaml.
        args: { person: string, text: string }
        job: { machine: .rook/blocks/tell.yaml, input: { person: "${args.person}", text: "${args.text}" }, approve: true }

    # agents/helper.yaml
    agent: helper
    include: .rook/agents/base.yaml
    model: { name: claude-sonnet-5-5, secret: ANTHROPIC_KEY }
    system: |
      You help the person who runs this computer. What you write is read on a phone:
      answer in one or two short sentences, in everyday words.

      Your tools are in parts, which you open with `open` when a question needs one.
      Open only what you need. A tool that changes something waits for a yes before
      it runs. On a long task, say how it is going with `progress`.

      ${input.format}
    open:
      messages: { include: parts/messages/part.yaml }

`approval.yaml` takes these, beside what Corbie gives an ask:

  part       the part's name
  people     people and groups in lookup.yaml who approve, each asked on their own bridge
  in         a Slack channel's #name, to ask them there in place of each one alone
  review     true to call review first; false by default
  alone      tools whose calls the review's yes approves with no person asked
  request    what was asked: the agent's input request, which the review and the people are shown

1. With `review: true`, approval calls `review` with the held call and the request, and reads `{ reply: { says, note } }`.
2. `refuse` ends it, and `yes` ends it for a tool in `alone`.
3. Anything else asks the people, shown the review's word. A review that fails or gives no `reply`, or a project with no `review.yaml`, shows them `Review failed:` and why.
4. A part whose ask names no people approves nothing, and says so to the agent.

    # review.yaml
    agent: review
    include: .rook/review/agent.yaml
    model: { name: claude-sonnet-5-5, secret: ANTHROPIC_KEY }

- The request and what the agent said are quoted, each line after `> `, so that no line of them reads as Rook's own.
- The agent is told who answered, as `alice said yes.`, or `No one answered in time, so the answer is no.`

- An agent that answers messages includes `.rook/agents/base.yaml`, and writes its own model, system text and parts.
- `base.yaml` gives the agent its input, its prompt, the conversation, and the tools `progress`, `look`, `send` and `form`.
- The tool `look` gets a file from `earlier` by its id, with its contents.
- The tool `send` sends a file where the message came from, at once: a blob the agent has, or a text it writes, under a name such as `report.csv`.

  Telegram    a document, which Telegram shows with a preview when it is an image
  Slack       a file in the conversation or thread, which the bot sends with the scope files:write
  GitLab      a comment that links the file, uploaded to the issue's project
  Jira        an attachment on the issue, and a comment that shows a PNG, JPEG or GIF and links any other

- `${input.format}` in the system text says how to write for the bridge the message came from.
- A part's script can call GitLab or Jira through the bridge's `api.js`. Its job names the file under `files:`, and allows the host and the secret, as the file's comment says.

Who gets what
-------------

`who.yaml` reads `rules.yaml`. A person gets the first agent that they and
everyone who reads the answer may each use, so what they get depends on where
they ask.

    # rules.yaml, of a team
    places:
      "#help": { readers: [anyone] }
      "#platform": { readers: [platform] }
      dm: { readers: [asker] }
    agents:
      - { name: team, for: [platform] }
      - { name: support, for: [anyone] }

  someone not in platform, anywhere        support
  someone in platform, in #help            support
  someone in platform, in dm or #platform  team

- A place that is not listed is read by anyone. A GitLab or Jira project must be listed for an agent that is not `for: [anyone]` to answer there.
- `readers:` names groups, `anyone` or `asker`. It is written in the file, and not read from a channel's members.
- `who.yaml` gives `rule`, the entry that chose the agent, so the chat's record shows why.
- A field that `rules.yaml` does not take, such as `words:` in an agent's entry, fails `who.yaml`, naming the field.
- When `rules.yaml` names an agent with no file in `agents/`, the person is told so.
- A part goes in an agent's file only if everyone in that agent's `for` may use it. Nothing checks this, and each mix of parts is its own agent file.
- The history comes from the thread the answer goes to. A bridge leaves out GitLab's internal notes and Jira's restricted comments, and does not hear them, since an answer on the issue is public.

Who may do what
---------------

1. Corbie's permissions apply first. A job may do only what its `allow:` says, within the ceilings, and a secret goes only to the host it is bound to.
2. An agent is allowed only its model. Its model can call its own tools (`progress`, `look`, `send`, `form`, `open` and Corbie's tools that read blobs) and the tools of the parts it has opened.
3. A tool marked `approve: true` waits for its part's ask.

Only the choice of agent limits what an answer can hold: a model cannot call
a tool its agent does not have, whatever its prompt says.

What Rook does not defend against
---------------------------------

- A tool that sends to a destination its arguments choose can send whatever the run read. Give it `approve: true`.
- A tool that names a person in its arguments needs `approve: true`. `progress` does not, since its text goes only to those who read the answer.
- Text a tool returns, such as an issue or a web page, and a thread's history, can tell the model to do things. Give each tool that changes something `approve: true`.
- Rook takes a message's sender from the service, and does not check it.
- Anyone who can change the directory can change every rule above but the first. Guard it by review in git.
